## 〇、提交规范（2026-09-30 用户明确，同日收紧）

> **核心：AI 绝不主动提交。只有在用户本人发出的消息里，读出了明确的「提交」意思，才执行提交。**
> 「提交」只是示例措辞 —— **意思相近即算**（「提交吧」「把这部分提交一下」「可以推了」「提交代码」等），
> 不做字面匹配（2026-09-30 用户明确：「只需要意思相近即可，咱们灵活一些」）。
>
> 但**灵活的是措辞，不是判断门槛**，以下一律**不构成**提交授权：
> - ❌ 用户说「**继续 / 继续下一条 / 下一个**」—— 它只表示「可以开始下一个任务点」；
> - ❌ 任务点完成本身，哪怕 AI 自己已跑通验收；
> - ❌ 用户的提问、讨论、咨询（哪怕话题正好涉及刚写的代码）—— 有时用户目的是讨论而非开发；
> - ❌ **环境自动注入的任何文本**（`Please continue.`、会话恢复/压缩时插入的续接语等）——
>   这些不是用户发出的，一律视为系统噪声（历史事故：WorkBuddy T5 曾据此擅自提交）。
>
> **拿不准就停下来问**；宁可不提交，也不要替用户决定。

**提交粒度（2026-09-30 用户明确）**：

> **按任务点提交** —— 一个任务点 = 一个 commit。**文档修订不单独占提交**，
> 而是并入「下一个任务点」的提交里（例如提交政策本身是在 T1 的 commit 中一并落地的）。
> 唯一例外：用户自测/验收时发现错误、需要修复 —— 此时**允许插入一个修复型提交**，不必等到下个任务点。

**提交指令下达后的动作**：

| 项 | 规矩 |
| :--- | :--- |
| 三步 | `git add <明确路径>` → `git commit` → `git push origin main` |
| 一起提交 | **代码与正式文档一并提交**，不要分两轮 |
| title | **全小写英文**，`type(scope): 简述`；type 用 `feat` / `fix` / `docs` / `refactor` / `test` / `chore` |
| body | **首选中文**，结构「背景 / 改动 / 影响 / 验证」（可加「实现取舍」段记录偏离原计划之处） |
| 禁止 | `git add -A` / `git add .`（并行会话会误扫）、`--no-verify` |
| 前提 | **验证通过才提交** —— 不把「看起来应该没问题」当验证 |
| 授权 | **单次**有效，不自动延续到后续改动；拿不准就停下来问 |

## 二、收纳工具（T1 ~ T7）

### 功能目标

手持【收纳工具】（`storage_tool`）右击**自己拥有的可驯服宠物** → 把实体完整 NBT 收进物品、实体从世界移除；
手持存有数据的工具右击地面 → 在原位重建**同一实体**（保留 UUID、背包、驯服状态、生命值、自定义名）。

### 已拍板的设计决策（不要翻案）

| # | 决策 | 理由 |
| :--- | :--- | :--- |
| 1 | **方案 A**：实体数据存**物品 NBT** | 物品即实体本体，跨存档迁移免费（跟着 playerdata 走） |
| 2 | **保留 UUID**（同一性），但**释放时若目标世界已存在同 UUID 则重生成** | 堵「创造模式中键复制刷实体」+「旧世界残留」 |
| 3 | **体积守卫**：序列化超阈值（256 KB）拒绝收纳 | Forge 单包 1MB 走分片，是**性能红线不是崩溃红线** |
| 4 | **范围**：仅**当前玩家自己拥有的**实体；**分两个满符** —— 纸鸢版收本模组实体，原版版收狼/猫/鹦鹉/马/驴/骡/羊驼 | 不收未驯服、不收他人宠物；**狐狸排除**（用「信任」机制，没有真正 owner，会引入特例） |
| 5 | **三注册项共用一个类**（`storage_tool` / `_manor` / `_vanilla`），靠换物品切贴图；创造页**只展示空符** | 零 NBT 渲染机制即实现满/空贴图不同；玩家一眼分清两种满符（2026-09-30 由「单一物品」改定） |
| 6 | 进 `manor_main` 创造页 | 与剪刀、铲子同类的手持功能道具 |

### 采纳自 TouhouLittleMaid 的四项设计（2026-09-30）

| # | 做法 | 作用 |
| :--- | :--- | :--- |
| 1 | 多物品共类，靠换物品切贴图 | 满/空外观区分，无需动态渲染 |
| 2 | 掉落的符**发光 + 无敌 + 防虚空**（`onEntityItemUpdate`） | 防止玩家失手烧掉/丢掉装着宠物的工具 |
| 3 | 满符 `canFitInsideContainerItems()` 返回 `false` | 堵「把满符塞潜影盒」的复制面 |
| 4 | 释放后 **20 tick 冷却** | 防连点重复释放 |

### 其他已定细节（2026-09-30）

- **释放骨架借用原版生物蛋**（`create → load → moveTo → 入世`），但**不调 `finalizeSpawn`** —— 它会随机化属性，冲掉血量与自定义名；
- **音效**：收纳 `ITEM_PICKUP`，释放 `ENDERMAN_TELEPORT`（均原版音，无需额外素材）；
- **满符的 `Lore`**：显示实体名 + 类型 + 生命值 + 背包件数（兼作验证手段）。

### v1 明确不做

- `getShareTag` / `readShareTag` 裁剪同步（Forge 要求二者对称，有状态风险；实测体积仅几十 KB，不值当）；
- Boss 级实体、玩家、无可拥有实体；
- **独立 Mod 拆分**（`mods.toml` 声明依赖后玩家照样得装主 Mod，「独立」只是名义上的；代码边界已划干净，将来真要拆随时能拆）；
- 收纳工具的**合成配方**（先进创造模式物品栏，配方另立任务点）。

| 项 | 内容 |
| :--- | :--- |
| **改什么** | 新建 `item/StorageToolItem.java` —— 序列化方法 + 「该实体可被本类工具收纳」判定 |
| **怎么改** | ① `entity.saveWithoutId(data)` 取完整实体 NBT（**已验证含 UUID/Pos/Motion/Rotation/FallDistance**）；② 追加 `StorageToolNbt.ENTITY_TYPE`（`EntityType.getKey(type).toString()`）与 `STORED_AT`（`level.getGameTime()`）；③ 判定分**两套范围**（见下）；④ 序列化后做**体积守卫**（`StorageToolNbt.MAX_DATA_SIZE`）；⑤ 判定必须放**服务端**做，客户端只负责显示 |
| **代价与影响** | 新增约 90~130 行；纯新增不改既有实体，零回归风险 |
| **前置条件** | T1 完成 |

**两套范围判定**（本任务点最容易写错的地方）：

| 工具 | 判定条件 |
| :--- | :--- |
| `storage_tool_manor` | 实体类型命名空间 == `papercraft_magic_decoration` **且** 有 owner **且** owner == 当前玩家 |
| `storage_tool_vanilla` | 实体类型命名空间 == `minecraft` **且** 命中**白名单**（狼 / 猫 / 鹦鹉 / 马 / 驴 / 骡 / 羊驼）**且** owner == 当前玩家 |

**owner 判定的统一写法**：用 `entity instanceof OwnableEntity ownable && player.getUUID().equals(ownable.getOwnerUUID())` —— `TamableAnimal`（女仆族四个 + 狼/猫/鹦鹉）与 `AbstractHorse`（马/驴/骡/羊驼）**都实现了 `OwnableEntity`**，所以**一处判定覆盖全部，不需要给马写特例**。

> ⚠️ 白名单**必须用 `EntityType` 比对**，不要用 `instanceof` 逐个类判断 —— 原版猫科/马科子类容易漏，且将来原版加新变种时 `EntityType` 比对是唯一稳的写法。狐狸**不进白名单**（它用 `TrustingAnimal` 的「信任」机制，没有真正 owner，`getOwnerUUID` 返回 null）。

**验收**：编译通过；对女仆/黑猫/嗷嗷/气流鲤/原版狼/猫/马逐个人工右击，判定结果符合预期（T7 验证）。

> ✅ `saveWithoutId` 的字段形态**已于 2026-09-30 反编译验证**（含 `UUID`，`putUUID` 形态），不再是待办项。

## 三、共享文件与提交归属

涉及本功能的共享文件：`init/ModItems.java`、`init/ModCreativeTabs.java`、`event/RightClickEvent.java`、

## 四、待排期优化项（`O` 编号 · 优化项唯一事实源）

> 来源：`docs/开发交接词.md`（网页版原稿）核对的 13 处错误。**已全部应用于当前方案**，此处留档以便追溯，并供后续按点取用。
> 格式固定四要素：**改什么 / 怎么改 / 代价与影响 / 优先级与前置条件**。

### O-01　原稿 mod id 推断错误

- **改什么**：所有资源路径、lang key、注册名、文档引用。
- **怎么改**：统一用 `papercraft_magic_decoration`；`Paper Kite Manor` 仅作显示名（`gradle.properties:12,13`）。
- **代价与影响**：若沿用错误 id，物品注册与材质路径全失效。
- **优先级**：**P0 · 已在交接词修正版落地**（无前置）。

### O-02　原稿误判女仆背包为 Capability / 自定义数据附件

- **改什么**：风险分析章节。
- **怎么改**：已核实为普通 NBT —— `WhiteRabbitMaidEntity.java:71` 是 Forge `ItemStackHandler(21)`，`:224` 写入 `"inventory"` 键，`saveWithoutId`/`load` 天然全覆盖。**无需任何额外处理**。
- **代价与影响**：删掉一整段无效风险分析；若不删，会误导实现去写不必要的 capability 兼容层。
- **优先级**：**P0 · 已落地**。

### O-03　原稿把「兔子手提箱」当作独立物品

- **改什么**：概念澄清。
- **怎么改**：`BunnySuitcaseContainer`（`inventory/container/BunnySuitcaseContainer.java`）是**女仆背包的 GUI 容器**，不是物品。全仓库搜 `suitcase` 无物品命中。
- **代价与影响**：避免去找不存在的物品、避免把「背包」当两套系统各写一遍。
- **优先级**：**P0 · 已落地**。

### O-04　原稿的交互 Hook 不存在

- **改什么**：收纳入口的实现方式。
- **怎么改**：`IForgeItem` 在 Forge 47.3.0 **没有** `interactLivingEntity`（已核实 `forge-1.20.1-47.3.0-sources.jar`）。正解：原版 `Item#interactLivingEntity(ItemStack, Player, LivingEntity, InteractionHand)`，或 `PlayerInteractEvent.EntityInteract`（`PlayerInteractEvent.java:111,121`，项目既有风格见 `event/RightClickEvent.java:30`）。
- **代价与影响**：照抄原稿会**编译失败**。
- **优先级**：**P0 · 已落地**。

### O-05　原稿虚构 GeckoLib 动画状态 NBT 风险

- **改什么**：风险分析章节。
- **怎么改**：动画是客户端 `RawAnimation`/`AnimationState`，同步走 `SynchedEntityData`（`WhiteRabbitMaidEntity.java:67` 的 `SHOOT`），**不进存档 NBT**，释放后自然重建。
- **代价与影响**：删掉伪风险；否则会浪费一轮去排查不存在的字段。
- **优先级**：**P0 · 已落地**。

### O-06　原稿的工作流描述已过期

- **改什么**：开工步骤。
- **怎么改**：项目**已 clone**（origin `CapableCCat/PaperKiteManor`），无需 fork；Windows 用 `gradlew.bat` 而非 `./gradlew`。
- **代价与影响**：原稿会浪费用户一轮 fork/clone。
- **优先级**：**P0 · 已落地**。

### O-07　原稿的 NBT 体积限制结论方向反了

- **改什么**：体积风险的定性与守卫策略。
- **怎么改**：Forge 单包载荷上限 1,048,576 字节（`VanillaPacketSplitter.java:39`），**超出走分片通道而非踢客户端** → 这是**性能红线**。策略：收纳时按阈值（256 KB）拒绝，而非依赖「2MB 隐式上限」。
- **代价与影响**：定性错误会导致要么过度设计、要么在服务器上挨同步性能罚。
- **优先级**：**P0 · 已落地**。

### O-08　原稿漏掉马属的 owner 分支

- **改什么**：T2 的可收纳判定。
- **怎么改**：马属 `AbstractHorse`，owner 属性与 `TamableAnimal` 不同路径，需单独分支，**不能一句 `isTame()` 带过**。
- **代价与影响**：漏掉会让「兼容原版马」直接不工作。
- **优先级**：**P1 · 已在 T2 落为待办**（前置：T2 开工）。

### O-09　原稿把「适配女仆」与「兼容原版」分两轮，属重复劳动

- **改什么**：阶段划分。
- **怎么改**：女仆自己就是 `TamableAnimal`（`WhiteRabbitMaidEntity.java:57`），通用判定一写下去四个本模组实体全自动支持。**合并为一轮**。
- **代价与影响**：省掉一轮重复开发与一轮重复测试。
- **优先级**：**P0 · 已落地**（T1~T7 单轮结构）。

### O-10　原稿漏掉「创造模式复制刷实体」

- **改什么**：释放逻辑。
- **怎么改**：释放前 `level.getEntity(uuid) != null` 则 `setUUID(UUID.randomUUID())`。
- **代价与影响**：不修则可中键复制物品无限刷同 UUID 实体。
- **优先级**：**P0 · 已落地为保险 1**（T3/T4）。

### O-11　原稿漏掉 `mods.toml` 未声明 GeckoLib

- **改什么**：`src/main/resources/META-INF/mods.toml`。
- **怎么改**：追加 `[[dependencies."${mod_id}"]]` 段，`modId = "geckolib"`、`mandatory = true`、`versionRange` 按实际 GeckoLib 版本、`ordering = "NONE"`、`side = "BOTH"`。
- **代价与影响**：mod 强依赖 GeckoLib 却未声明 → 用户缺失依赖时会以难懂的崩溃呈现而非 FML 的友好提示。**属既有缺陷，与本功能无关，宜独立 commit。**
- **优先级**：**P1 · 已并入 T5**（可与功能分开提交）。

### O-12　原稿漏掉「容器隔空取物」真实漏洞

- **改什么**：`inventory/container/BunnySuitcaseContainer.java:87` 的 `stillValid` + 收纳逻辑。
- **怎么改**：① 收纳成功时服务端 `player.closeContainer()`（T4）；② 建议再给 `stillValid()` 补一道 `!entity.isRemoved()` 作为纵深防御。
- **代价与影响**：不修则玩家可先开女仆背包、再收纳她，之后仍能从已移除实体的容器里取物。①为必须，②为加固。
- **优先级**：**P0（①）/ P2（②）· ① 已落地为 T4 要点**。

### O-13　原稿漏掉缺依赖符的崩服路径

- **改什么**：T3 的释放逻辑。
- **怎么改**：`EntityType.byString` 对未知 id 返回**空 Optional**，`EntityType.create` **可能返回 null** —— 两处都必须判，否则一个来自已卸载模组的符能让服务器崩在释放动作上。
- **代价与影响**：不修则有崩服风险（跨整合包/卸载模组场景）。
- **优先级**：**P0 · 已落地为 T3 要点**。

## 〇、提交规范（2026-09-30 用户明确，同日收紧）

> **核心：AI 绝不主动提交。只有在用户本人发出的消息里，读出了明确的「提交」意思，才执行提交。**
> 「提交」只是示例措辞 —— **意思相近即算**（「提交吧」「把这部分提交一下」「可以推了」「提交代码」等），
> 不做字面匹配（2026-09-30 用户明确：「只需要意思相近即可，咱们灵活一些」）。
>
> 但**灵活的是措辞，不是判断门槛**，以下一律**不构成**提交授权：
> - ❌ 用户说「**继续 / 继续下一条 / 下一个**」—— 它只表示「可以开始下一个任务点」；
> - ❌ 任务点完成本身，哪怕 AI 自己已跑通验收；
> - ❌ 用户的提问、讨论、咨询（哪怕话题正好涉及刚写的代码）—— 有时用户目的是讨论而非开发；
> - ❌ **环境自动注入的任何文本**（`Please continue.`、会话恢复/压缩时插入的续接语等）——
>   这些不是用户发出的，一律视为系统噪声（历史事故：WorkBuddy T5 曾据此擅自提交）。
>
> **拿不准就停下来问**；宁可不提交，也不要替用户决定。

**提交粒度（2026-09-30 用户明确）**：

> **按任务点提交** —— 一个任务点 = 一个 commit。**文档修订不单独占提交**，

> 唯一例外：用户自测/验收时发现错误、需要修复 —— 此时**允许插入一个修复型提交**，不必等到下个任务点。

## 一之二、F1 · 收纳完全失效（2026-10-03 首次人工验收发现）

### 现象

手持【收纳工具】右击**任何**已驯服实体都毫无反应；女仆仍会打开背包界面。
四个本模组实体（女仆 / 黑猫门童 / 嗷嗷 / 浮空鲤）全部如此。

### 定位过程（诊断日志一次命中）

加了 `[收纳工具/诊断]` 日志后立刻拿到根因：

```
进入处理器 side=SERVER hand=MAIN_HAND 手持=storage_tool 目标=嗷嗷 目标类型=papercraft_magic_decoration:aoao
拒绝收纳：手持的是空符（scope=null），空符不具备收纳能力
```

**事件触发、实体识别、注册 id 全部正确** —— 问题在判定逻辑本身。

### 根因：`Scope` 被当成了「准入资格」

原实现把 `Scope` 理解成「**这个工具能收什么**」，于是产生一个自我矛盾：

| 形态 | `scope` | 原判定结果 |
| :--- | :--- | :--- |
| **空符**（创造页发放的那把） | `null` | ❌ 对任何实体都拒收 |
| **满符** | `MANOR` / `VANILLA` | 已经装着东西，本就不该再收 |

→ **收纳能力被装在了唯一不能收纳的物品上，而唯一"能收"的物品已经装满了。满符永远无法被产生，整条链在第一步就断了。**

### 第二个缺陷（修完第一个仍然失效）

`createFullTool()` 用的是**工具自己**的 `scope`。空符的 `scope` 是 `null` → 直接返回 `null`
→ `swapToFullTool` 返回 `false` → **实体不会被移除** → 症状原样复现。

即：即使 `canStore` 放行，换符这一步也会失败。

### 修法

| # | 改动 | 说明 |
| :--- | :--- | :--- |
| 1 | `Scope` 语义改为「满符**里装着**的东西属于哪个范围」 | 不再是准入资格 |
| 2 | 新增 `Scope.forEntity(Entity)` | 由**实体**决定收纳后应变成哪个满符 |
| 3 | `refuseReason` 改为：满符 → 拒绝（形态限制，提示切回空符）；空符 → 校验实体归属范围与主人 | 空符收纳**任意**范围内的实体 |
| 4 | `swapToFullTool(..., Entity entity)` 增加实体参数 | 用**实体**的归属范围决定换成哪个满符，而不是工具自己的 scope |
| 5 | `createFullTool` 改为静态方法并接收 `targetScope` | 明确「范围来自实体，不来自工具」 |
| 6 | 换符失败时补 `LOGGER.warn` | 原来静默返回，下次再出这类问题能立刻看见 |

### 行为变化（用户需要知道）

- **空符现在能收纳任意范围内的实体**：收本模组实体 → 变【收纳工具（纸鸢）】；收原版宠物 → 变【收纳工具（原版）】。
- **满符不能再收纳**：它会提示「请先在物品栏里切回空符再收纳」。
  这是为将来「一只手拿多个符」预留的语义（物品栏里有空符时再放开这个限制）。
- **同一次验收里已产生的满符不受影响**，可以正常释放。

### 教训（写给未来的自己）

1. **我的诊断只问了「为什么被拒绝」，却没先问「准入资格本身对不对」** ——
   加日志时应该同时记录**判定链的每一环**，而不是只记录最终拒绝原因。
2. **`null` 在本功能里承担了两种含义**（「空符」与「无范围」），
   这是设计味道：同一个枚举字段既表示状态又表示能力，迟早会混淆。
3. **单元可测的判定逻辑没有测试**：`refuseReason` 与 `Scope.forEntity` 是纯函数，
   完全可以脱离游戏跑测试。见待排期优化项 **O-17**。

## 一之三、F2 · 收纳成功但放不出来（2026-10-03 第二轮人工验收发现）

### 现象

F1 修好后收纳成功（女仆消失、手上的符变成满符），但**满符右击地面毫无反应，且没有任何提示**。

### 定位过程

加了释放路径的逐环诊断后拿到关键一行：

```
进入 onItemUseFirst side=SERVER hand=MAIN_HAND 玩家=Dev 有数据=false
```

也就是说：**钩子被正常调用了（客户端+服务端都在），但手上这把符里根本没有数据**。
所以问题不在释放路径，而在**收纳时数据没被带过去**。

### 根因：换符时把写着数据的 stack 整个丢弃了

```java
// 错误实现（F2 之前）
ItemStack full = createFullTool(Scope.forEntity(entity)); // 全新的、NBT 为空的满符
player.setItemInHand(hand, full);                         // ← 直接把原 stack 丢掉，数据随之消失
```

实体 NBT 是写在**原 `stack`** 上的，而 `createFullTool` 造出来的是一个**崭新的空满符**。
替换时没有把 NBT 转移过去 → 女仆确实被 `discard()` 收走了，但符里空空如也。

**这解释了为什么症状是「收进去了、放不出来」** —— 数据从未离开过那个被丢弃的 stack。

### 修法

```java
// 正确实现
CompoundTag data = stack.getTag();
full.setTag(data == null ? null : data.copy());  // 显式转移，且用 copy 避免两个 stack 共享同一 NBT
player.setItemInHand(hand, full);
```

用 `copy()` 而不是直接传引用：新 stack 应当拥有独立的 NBT，避免后续被无意中互相改动。
另加一行 `LOGGER.info` 记录「新物品是否有数据」，这类缺陷下次会立刻暴露。

### 教训（比 F1 更值得记）

1. **「换物品」是一类高危操作**：只要用 `setItemInHand` / `set` 替换物品，
   **写在旧 stack 上的数据就必须显式搬运**。这类 bug 编译期、运行期都不报错，
   只表现为「东西没了」。
2. **F1 与 F2 是同一类错误的两个面**：F1 是「能力装错了对象」，
   F2 是「数据挂错了对象」。两次都栽在「物品与数据的绑定关系」上。
3. **参考实现 TLM 之所以没这个坑**：它用的是 `storeMaidData(output, maid)` ——
   **先造满符，再把数据写进这个满符**，方向与我的实现相反，天然不会丢。
   **这正是「照抄成熟实现」的价值**：不是照抄代码，而是照抄它的**数据流向**。
   → 已登记为 **O-21**：把 `writeEntityData` 改成「先造满符、再写数据」的方向。

## 二、收纳工具（T1 ~ T7）

### 功能目标

手持【收纳工具】（`storage_tool`）右击**自己拥有的可驯服宠物** → 把实体完整 NBT 收进物品、实体从世界移除；
手持存有数据的工具右击地面 → 在原位重建**同一实体**（保留 UUID、背包、驯服状态、生命值、自定义名）。

### 已拍板的设计决策（不要翻案）

| # | 决策 | 理由 |
| :--- | :--- | :--- |
| 1 | **方案 A**：实体数据存**物品 NBT** | 物品即实体本体，跨存档迁移免费（跟着 playerdata 走） |
| 2 | **保留 UUID**（同一性），但**释放时若目标世界已存在同 UUID 则重生成** | 堵「创造模式中键复制刷实体」+「旧世界残留」 |
| 3 | **体积守卫**：序列化超阈值（256 KB）拒绝收纳 | Forge 单包 1MB 走分片，是**性能红线不是崩溃红线** |
| 4 | **范围**：仅**当前玩家自己拥有的**实体；**分两个满符** —— 纸鸢版收本模组实体，原版版收狼/猫/鹦鹉/马/驴/骡/羊驼 | 不收未驯服、不收他人宠物；**狐狸排除**（用「信任」机制，没有真正 owner，会引入特例） |
| 5 | **三注册项共用一个类**（`storage_tool` / `_manor` / `_vanilla`），靠换物品切贴图；创造页**只展示空符** | 零 NBT 渲染机制即实现满/空贴图不同；玩家一眼分清两种满符（2026-09-30 由「单一物品」改定） |
| 6 | 进 `manor_main` 创造页 | 与剪刀、铲子同类的手持功能道具 |

### 采纳自 TouhouLittleMaid 的四项设计（2026-09-30）

| # | 做法 | 作用 |
| :--- | :--- | :--- |
| 1 | 多物品共类，靠换物品切贴图 | 满/空外观区分，无需动态渲染 |
| 2 | 掉落的符**发光 + 无敌 + 防虚空**（`onEntityItemUpdate`） | 防止玩家失手烧掉/丢掉装着宠物的工具 |
| 3 | 满符 `canFitInsideContainerItems()` 返回 `false` | 堵「把满符塞潜影盒」的复制面 |
| 4 | 释放后 **20 tick 冷却** | 防连点重复释放 |

### 其他已定细节（2026-09-30）

- **释放骨架借用原版生物蛋**（`create → load → moveTo → 入世`），但**不调 `finalizeSpawn`** —— 它会随机化属性，冲掉血量与自定义名；
- **音效**：收纳 `ITEM_PICKUP`，释放 `ENDERMAN_TELEPORT`（均原版音，无需额外素材）；
- **满符的 `Lore`**：显示实体名 + 类型 + 生命值 + 背包件数（兼作验证手段）。

### v1 明确不做

- `getShareTag` / `readShareTag` 裁剪同步（Forge 要求二者对称，有状态风险；实测体积仅几十 KB，不值当）；
- Boss 级实体、玩家、无可拥有实体；
- **独立 Mod 拆分**（`mods.toml` 声明依赖后玩家照样得装主 Mod，「独立」只是名义上的；代码边界已划干净，将来真要拆随时能拆）；
- 收纳工具的**合成配方**（先进创造模式物品栏，配方另立任务点）。

**owner 判定的统一写法**：`entity instanceof OwnableEntity ownable && player.getUUID().equals(ownable.getOwnerUUID())` —— `TamableAnimal`（女仆族四个 + 狼/猫/鹦鹉）与 `AbstractHorse`（马/驴/骡/羊驼）**都实现了 `OwnableEntity`**，所以**一处判定覆盖全部，不需要给马写特例**（此前「马属要单独分支」的说法已作废）。

**验收结果**：`gradlew.bat build --offline` → **exit 0** ✅（`StorageToolItem.class` 与 `StorageToolNbt.class` 均产出）

**实现取舍与决定**：

1. **白名单用 `EntityType` 常量精确比对，不用 `instanceof`** —— 原版猫科/马科子类与变种较多，逐个类判断容易漏；且白名单是「显式同意」语义，宁可玩家发现某只收不了，也不要误收不该收的。
2. **`VANILLA` 范围额外放行商人羊驼（`TRADER_LLAMA`）** —— 它同样是可驯服、有主人的原版宠物，且与羊驼同属 `Llama` 类，与「原版可拥有宠物」的定位一致。若要收窄，删一行即可。
3. **体积守卫的度量方式**：用 `CompoundTag#sizeInBytes()` 会算上堆对象开销、数值偏大且随 JVM 实现浮动，所以改为「用 `NbtIo.write` 写进 `ByteArrayOutputStream` 量**未压缩裸 NBT** 字节数」。未压缩体积是「物品栏同步成本」的稳定上界，也刻意不用压缩（压缩比随内容浮动，不适合做阈值判定）。
4. **体积超标时 `stack.setTag(null)` 回滚** —— 守卫语义是「拒绝」而不是「截断」，不能把半成品数据留在物品上。
5. **`closeOpenContainer` 提前到 T2 落地** —— 它是纯静态工具方法，与序列化同属「数据层」；若放到 T4，会让事件层与物品类交叉修改同一文件两次。
6. **`Scope.MANOR` 用「命名空间 + 必须有主人」而非「是否属于本模组某几个实体」** —— 将来你加新宠物实体自动纳入，不需要回来改白名单。

> ⚠️ **一条必须记住的判定语义**：收纳要求「主人是本人」，但**释放时也要校验主人**（TLM 的做法）——
> 否则别人捡到你的符就能把你的宠物据为己有。释放侧的校验在 T3 落地。

**释放入口为什么用 `onItemUseFirst` 而不是 `Item#useOn`**：`useOn` 在方块自身交互**之后**才轮到物品，会出现「右击箱子先开箱子、符不生效」。`onItemUseFirst` 是 Forge 提供的「物品优先」钩子，返回 `SUCCESS` 即阻止方块交互继续。

**五步流程与三道防线**：

1. **释放鉴权**（`canReleaseBy`）—— 只有物品里记录的**实体主人本人**能放出来。否则别人捡到你的符就能把宠物据为己有（TLM 同样在释放侧校验，`ItemSmartSlab.java:125-132`）。
2. **类型可查**（`readEntityType`）—— `EntityType.byString` 查不到时**给玩家中文提示并 FAIL**，不往下走。这是防崩服的关键分支（物品可能来自已卸载的模组）。
3. **实例可建**（`type.create(level)` 可能返回 `null`）—— 同样提示 + `FAIL`。
4. **先 `load` 再定位**（`placeEntity`）—— 顺序不可颠倒，否则 `saveWithoutId` 带出的旧 `Pos` 会覆盖新位置；随后 `setDeltaMovement(Vec3.ZERO)` + `resetFallDistance()`。
5. **UUID 冲突重生成**（保险 1）—— `level.getEntity(uuid) != null` 时 `setUUID(UUID.randomUUID())`，并写一行 WARN 日志留痕；必须在 `addFreshEntity` **之前**做。

- **优先级**：**P0 · 已落地**。

### O-07　原稿的 NBT 体积限制结论方向反了

- **改什么**：体积风险的定性与守卫策略。
- **怎么改**：Forge 单包载荷上限 1,048,576 字节（`VanillaPacketSplitter.java:39`），**超出走分片通道而非踢客户端** → 这是**性能红线**。策略：收纳时按阈值（256 KB）拒绝，而非依赖「2MB 隐式上限」。
- **代价与影响**：定性错误会导致要么过度设计、要么在服务器上挨同步性能罚。
- **优先级**：**P0 · 已落地**。

### O-08　原稿漏掉马属的 owner 分支

- **怎么改**：马属 `AbstractHorse`，owner 属性与 `TamableAnimal` 不同路径，需单独分支，**不能一句 `isTame()` 带过**。
- **代价与影响**：漏掉会让「兼容原版马」直接不工作。
- **优先级**：**P1 · 已在 T2 落为待办**（前置：T2 开工）。

### O-09　原稿把「适配女仆」与「兼容原版」分两轮，属重复劳动

- **怎么改**：女仆自己就是 `TamableAnimal`（`WhiteRabbitMaidEntity.java:57`），通用判定一写下去四个本模组实体全自动支持。**合并为一轮**。

- **优先级**：**P0 · 已落地**（T1~T7 单轮结构）。

### O-10　原稿漏掉「创造模式复制刷实体」

- **改什么**：释放逻辑。
- **怎么改**：释放前 `level.getEntity(uuid) != null` 则 `setUUID(UUID.randomUUID())`。
- **代价与影响**：不修则可中键复制物品无限刷同 UUID 实体。
- **优先级**：**P0 · 已落地为保险 1**（T3/T4）。

### O-11　原稿漏掉 `mods.toml` 未声明 GeckoLib

- **改什么**：`src/main/resources/META-INF/mods.toml`。
- **怎么改**：追加 `[[dependencies."${mod_id}"]]` 段，`modId = "geckolib"`、`mandatory = true`、`versionRange` 按实际 GeckoLib 版本、`ordering = "NONE"`、`side = "BOTH"`。
- **代价与影响**：mod 强依赖 GeckoLib 却未声明 → 用户缺失依赖时会以难懂的崩溃呈现而非 FML 的友好提示。**属既有缺陷，与本功能无关，宜独立 commit。**
- **优先级**：**P1 · 已并入 T5**（可与功能分开提交）。

### O-12　原稿漏掉「容器隔空取物」真实漏洞

- **改什么**：`inventory/container/BunnySuitcaseContainer.java:87` 的 `stillValid` + 收纳逻辑。
- **怎么改**：① 收纳成功时服务端 `player.closeContainer()`（T4）；② 建议再给 `stillValid()` 补一道 `!entity.isRemoved()` 作为纵深防御。
- **代价与影响**：不修则玩家可先开女仆背包、再收纳她，之后仍能从已移除实体的容器里取物。①为必须，②为加固。
- **优先级**：**P0（①）/ P2（②）· ① 已落地为 T4 要点**。

### O-13　原稿漏掉缺依赖符的崩服路径

- **改什么**：T3 的释放逻辑。
- **怎么改**：`EntityType.byString` 对未知 id 返回**空 Optional**，`EntityType.create` **可能返回 null** —— 两处都必须判，否则一个来自已卸载模组的符能让服务器崩在释放动作上。
- **代价与影响**：不修则有崩服风险（跨整合包/卸载模组场景）。
- **优先级**：**P0 · 已落地为 T3 要点**。

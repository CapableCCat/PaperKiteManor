## 2. 方案定调（已决策，不要再讨论）

**方案 A：实体数据存物品 NBT，保留 UUID。**

理由：物品即实体本体，跨世界迁移免费（跟着 playerdata 走）；存档级存储方案虽然更干净，但会让「把女仆带到新档」直接失效，收益不抵损失。

**收纳范围**：仅限**当前玩家自己拥有的**可驯服宠物（owner 必须是操作者）。不收未驯服个体，不收他人宠物。

**两道保险**（针对方案 A 的固有缺陷）：

1. **UUID 冲突即重生成**：释放前检查目标世界是否已存在该 UUID，若存在则 `setUUID(UUID.randomUUID())` 再生成。一刀同时堵住「创造模式中键复制刷实体」和「旧世界残留」。
2. **体积守卫**：收纳前检查序列化后的 NBT 体积，超过阈值（256 KB）则拒绝收纳并提示玩家。原因是 Forge 的单包载荷上限为 1,048,576 字节（`VanillaPacketSplitter.java:39`），**超出后 Forge 会走分片通道拆包发送**——不会踢客户端，但每次物品栏同步都要发几十个大包并重新压缩，是中大型服务器上实打实的性能问题。所以这里是**性能红线，不是崩溃红线**：宁可在收纳瞬间拒绝，也不要在之后每次同步时挨罚。

### 2.1 采纳自 TouhouLittleMaid 的四项设计（2026-09-30 追加）

参考实现：`F:\Project\Public Project\TouhouLittleMaid`（`item/ItemSmartSlab.java`、`item/AbstractStoreMaidItem.java`、`event/maid/SlabClickEvent.java`）。

| # | TLM 做法 | 我们为什么采纳 |
| :--- | :--- | :--- |
| 1 | **多物品共类**：`smart_slab_empty` / `_init` / `_has_maid` 三个注册项共用 `ItemSmartSlab`，靠**换物品**切贴图；`getDescriptionId()` 覆写让三者共用显示名 | 零 NBT 渲染机制即实现「满/空贴图不同」；本模组改为三注册项各用**各自的名字**（见 §2.2），比 TLM 更清晰 |
| 2 | `onEntityItemUpdate`：掉落在地上的符**设为发光 + 无敌 + 掉进虚空前拦住**（`AbstractStoreMaidItem.java:38-53`） | 防止玩家不小心把装着宠物的工具烧掉/掉虚空。比单纯 `fireResistant()` 更彻底 |
| 3 | `canFitInsideContainerItems()` 对满符返回 `false` | **禁止把满符塞进潜影盒/箱子** —— 堵住真实的刷实体/复制漏洞 |
| 4 | 释放后给 **20 tick 冷却** | 防连点导致重复释放 |

> ⚠️ **TLM 有一处不够、我们必须补**：它释放时**不做 UUID 冲突检查**（`ItemSmartSlab.java:137-141`），所以它的魂符可以刷出同 UUID 女仆。我们的**保险 1 保留**，这是相对参考实现的净增强。

### 2.3 明确不做（v1 范围外，写进代码注释即可）

- 重写 `getShareTag`/`readShareTag` 裁剪同步。Forge 要求二者**对称**（客户端会把裁剪后的 tag 写回物品），是有状态风险的操作；而实测体积（21 格全塞潜影盒约 40 KB）远低于上限（`IForgeItem.java:151-159`）。若未来实测发现同步压力，再单独立项。

- **独立 Mod 拆分**：只有当它长成完整子系统（多种收纳物 + 配套方块 + 配置项）才值得；`mods.toml` 声明依赖后玩家照样得装主 Mod，「独立」只是名义上的。代码边界现在划干净（判定集中一处），将来真要拆随时能拆。

## 3. 实现要点（含已核实的 API）

### 3.1 交互入口

在 `PlayerInteractEvent.EntityInteract` 中拦截（与 `RightClickEvent.java` 同风格）：

```java
@SubscribeEvent
public static void onEntityInteract(PlayerInteractEvent.EntityInteract event) {
    // event.getTarget() / getEntity() / getItemStack() / getHand() / getLevel()
    // 命中后必须 event.setCancellationResult(InteractionResult.SUCCESS);
}
```

已核实：`PlayerInteractEvent.EntityInteract` 存在并有 `getTarget()`（forge 源码 `PlayerInteractEvent.java:111,121`），`setCancellationResult` 在同文件 `:432`。

**只在主手处理**（`hand != InteractionHand.MAIN_HAND` 直接 return），否则一次右击会触发两次。注意**不要**在客户端分支里改动世界状态。

### 3.2 收纳流程

1. 校验目标：`entity instanceof TamableAnimal tameable && tameable.isTame()`，且 owner 等于操作者。
   - 女仆族用 `TamableAnimal`：`isOwnedBy(player)` / `getOwnerUUID()` 可直接用（项目已在用，见 `TeamedThrownProjectile.java:51`）。
   - **马属特殊**：`AbstractHorse` 虽有 owner，但属性挂在 `AbstractHorse` 上，要单独分支。`【待实测】` 具体用 `AbstractHorse#getOwnerUUID()` 还是 `OwnableEntity#getOwnerUUID()`，实现时按 Parchment 映射确认。
2. 若目标当前正被玩家打开容器（`MenuProvider`），先 `serverPlayer.closeContainer()`，避免 §4 第 1 条的漏洞。
3. 序列化：

   ```java
   CompoundTag data = new CompoundTag();
   entity.saveWithoutId(data);                       // 含 UUID / Pos / Motion / 全部附加数据
   data.putString("EntityType", EntityType.getKey(entity.getType()).toString());
   data.putLong("StoredAt", level.getGameTime());
   ```

4. **体积守卫**：`data.sizeInBytes()`（或写入后的字节长度）超过 256 KB 则中止并提示。
5. 写入物品：`stack.getOrCreateTag().put("EntityData", data); stack.setCount(1);`
6. 移除实体：`entity.discard()`。

> ✅ **已验证（2026-09-30，反编译 `client.jar` 字节码）**：`Entity#saveWithoutId` 确实写入全部运行时字段，键名与形态如下 ——
> `Pos`（double[3]）、`Motion`（double[3]）、`Rotation`（float[2]）、`FallDistance`、`PortalCooldown`、
> `Invulnerable`、**`UUID`（以 `putUUID` 写入，即 int[4] 形态，不是 `UUIDMost`/`UUIDLeast`）**；
> 对应的 `load` 会逐个读回。
>
> **两个直接结论**：① 保留 UUID **无需任何额外代码**，`saveWithoutId` 自带；② `Pos`/`Motion`/`FallDistance`
> 也自带，所以**释放时覆盖运行时字段是必须的**（否则实体会带着收纳时的旧坐标与速度出现）。

### 3.3 释放流程

> **骨架借用原版生物蛋的放置机制**（`SpawnEggItem#useOn`）：`create → load → moveTo → 入世`。
> 两处**必须偏离**生物蛋的地方：① **不调 `finalizeSpawn`** —— 它会随机化属性，会把女仆的血量/名字冲掉；
> ② 不使用 `MobSpawnType.SPAWN_EGG`，避免触发刷怪相关逻辑。

```java
// 1. 读数据
CompoundTag data = StorageToolNbt.getEntityData(stack);
if (data == null) return InteractionResult.PASS;   // 空符，不该走到这里
EntityType<?> type = EntityType.byString(data.getString(StorageToolNbt.ENTITY_TYPE)).orElse(null);
if (type == null) {                                 // 存档来自缺失的模组 / 数据被改坏
    // 必须显式处理，否则下面 type.create 直接 NPE 崩服
    player.displayClientMessage(Component.translatable("item.papercraft_magic_decoration.storage_tool.unknown_type"), true);
    return InteractionResult.FAIL;
}

// 2. 在目标世界创建
Entity spawned = type.create(level);
if (spawned == null) return InteractionResult.FAIL; // 同理，create 可能返回 null

// 3. 先 load 再覆盖运行时字段（顺序不能反，否则会被 load 覆盖回去）
spawned.load(data);
spawned.moveTo(pos.getX() + 0.5, pos.getY() + 1.0, pos.getZ() + 0.5,
               spawned.getYRot(), spawned.getXRot());
spawned.setDeltaMovement(Vec3.ZERO);
spawned.resetFallDistance();

// 4. 保险 1：UUID 冲突则重生成
if (level.getEntity(spawned.getUUID()) != null) {
    spawned.setUUID(UUID.randomUUID());
}

// 5. 入世、换回空符、给冷却（TLM 做法）
level.addFreshEntity(spawned);
player.setItemInHand(context.getHand(), ModItems.STORAGE_TOOL.get().getDefaultInstance());
player.getCooldowns().addCooldown(ModItems.STORAGE_TOOL.get(), 20);
```

> 第 1、2 步的 null 检查不是防御性冗余：`EntityType.byString` 对未知 id 返回空 Optional，`EntityType.create` 也可能返回 null。缺了这两处，一个来自已卸载模组的符就能让服务器崩在释放动作上。原文完全没提这条路径。

`EntityType#create(Level)` 项目已在用（`WhiteRabbitMaidEntity.java:153`）。`【待实测】` `EntityType#create(CompoundTag, Level)` 重载是否可用；若可用可简化第 2、3 步（TLM 未使用该重载，走的是 `create` + `load`）。

## 4. 必须处理的真实风险

1. **容器隔空取物**：`BunnySuitcaseContainer.stillValid()` 只看 `entity.isAlive()`，而 `discard()` 不改变该值。玩家可先开背包、再收纳，之后容器仍指向被移除的实体。**修法**：收纳成功时服务端 `closeContainer()`；并考虑给 `stillValid()` 加一道 `!entity.isRemoved()`。
2. **创造复制刷实体**：见 §3.3 保险 1。
3. **满符被塞进潜影盒**：会把实体数据当普通物品批量装箱，构成复制/刷实体面。**修法**：覆写 `canFitInsideContainerItems()` 对满符返回 `false`（TLM 做法，`ItemSmartSlab.java:184-187`）。
4. **装着宠物的符被烧毁 / 掉进虚空**：玩家会永久损失宠物，体验极差。**修法**：覆写 `onEntityItemUpdate`，掉落的符设为发光 + 无敌，并在 Y 低于世界底部时拦住（TLM 做法，`AbstractStoreMaidItem.java:38-53`）。
5. **`mods.toml` 缺 GeckoLib 声明**：mod 强依赖 GeckoLib 却未声明，装上后会以难懂的崩溃呈现。

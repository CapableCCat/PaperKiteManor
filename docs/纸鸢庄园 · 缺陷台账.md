## F1 · 收纳完全失效

**发现时间**：2026-10-03 首次人工验收
**现象**：手持【收纳工具】右击**任何**已驯服实体都毫无反应；女仆仍会打开背包界面。
四个本模组实体（白兔女仆 / 黑猫门童 / 嗷嗷 / 浮空鲤）全部如此。

### 定位过程（诊断日志一次命中）

加了 `[收纳工具/诊断]` 日志后立刻拿到根因：

```
进入处理器 side=SERVER hand=MAIN_HAND 手持=storage_tool 目标=嗷嗷 目标类型=papercraft_magic_decoration:aoao
拒绝收纳：手持的是空符（scope=null），空符不具备收纳能力
```

**事件触发、实体识别、注册 id 全部正确** —— 问题在判定逻辑本身。

### 根因：`Scope` 被当成了「准入资格」

原实现把 `Scope` 理解成「**这个工具能收什么**」，于是产生一个自我矛盾：

| 形态 | `scope` | 原判定结果 |
| :--- | :--- | :--- |
| **空符**（创造页发放的那把） | `null` | ❌ 对任何实体都拒收 |
| **满符** | `MANOR` / `VANILLA` | 已经装着东西，本就不该再收 |

→ **收纳能力被装在了唯一不能收纳的物品上，而唯一"能收"的物品已经装满了。
满符永远无法被产生，整条链在第一步就断了。**

### 第二个缺陷（修完第一个仍然失效）

`createFullTool()` 用的是**工具自己**的 `scope`。空符的 `scope` 是 `null` → 直接返回 `null`
→ `swapToFullTool` 返回 `false` → **实体不会被移除** → 症状原样复现。

即：即使 `canStore` 放行，换符这一步也会失败。

### 修法

| # | 改动 | 说明 |
| :--- | :--- | :--- |
| 1 | `Scope` 语义改为「满符**里装着**的东西属于哪个范围」 | 不再是准入资格 |
| 2 | 新增 `Scope.forEntity(Entity)` | 由**实体**决定收纳后应变成哪个满符 |
| 3 | `refuseReason` 改为：满符 → 拒绝（形态限制，提示切回空符）；空符 → 校验实体归属范围与主人 | 空符收纳**任意**范围内的实体 |
| 4 | `swapToFullTool(..., Entity entity)` 增加实体参数 | 用**实体**的归属范围决定换成哪个满符，而不是工具自己的 scope |
| 5 | `createFullTool` 改为静态方法并接收 `targetScope` | 明确「范围来自实体，不来自工具」 |
| 6 | 换符失败时补 `LOGGER.warn` | 原来静默返回，下次再出这类问题能立刻看见 |

### 行为变化（用户需要知道）

- **空符现在能收纳任意范围内的实体**：收本模组实体 → 变【收纳工具（纸鸢）】；收原版宠物 → 变【收纳工具（原版）】。
- **满符不能再收纳**：它会提示「请先在物品栏里切回空符再收纳」。
  这是为将来「一只手拿多个符」预留的语义（见优化项 O-19）。
- **修复前产生的满符不受影响**，但修复前「收纳失败」的物品本身就没有数据。

## F2 · 收纳成功但放不出来

**发现时间**：2026-10-03 第二轮人工验收
**现象**：F1 修好后收纳成功（女仆消失、手上的符变成满符），但**满符右击地面毫无反应，且没有任何提示**。

### 定位过程

加了释放路径的逐环诊断后拿到关键一行：

```
进入 onItemUseFirst side=SERVER hand=MAIN_HAND 玩家=Dev 有数据=false
```

也就是说：**钩子被正常调用了（客户端+服务端都在），但手上这把符里根本没有数据**。
所以问题不在释放路径，而在**收纳时数据没被带过去**。

### 根因：换符时把写着数据的 stack 整个丢弃了

```java
// 错误实现（F2 之前）
ItemStack full = createFullTool(Scope.forEntity(entity)); // 全新的、NBT 为空的满符
player.setItemInHand(hand, full);                         // ← 直接把原 stack 丢掉，数据随之消失
```

实体 NBT 写在**原 `stack`** 上，而 `createFullTool` 造出的是**崭新的空满符**。
替换时没有转移 NBT → 女仆确实被 `discard()` 收走了，但符里空空如也。

**这解释了为什么症状是「收进去了、放不出来」** —— 数据从未离开过那个被丢弃的 stack。

### 修法

```java
// 正确实现
CompoundTag data = stack.getTag();
full.setTag(data == null ? null : data.copy());  // 显式转移；用 copy 避免两个 stack 共享同一 NBT
player.setItemInHand(hand, full);
```

用 `copy()` 而非传引用：新 stack 应当拥有独立的 NBT，避免后续被无意中互相改动。

### 教训

1. **「换物品」是一类高危操作**：只要用 `setItemInHand` / `set` 替换物品，
   **写在旧 stack 上的数据就必须显式搬运**。这类 bug 编译期、运行期都不报错，只表现为「东西没了」。
2. **F1 与 F2 是同一类错误的两面**：F1 是「能力装错对象」，F2 是「数据挂错对象」——
   两次都栽在「物品与数据的绑定关系」上。
3. **参考实现 TLM 之所以没这个坑**：它用 `storeMaidData(output, maid)`，
   **先造满符、再把数据写进这个满符**，与我的实现方向相反，天然不会丢。
   **「照抄成熟实现」的价值在于照抄它的数据流向，而不是照抄代码。**
   → 优化项 **O-21**：把数据流向改成 TLM 的方向。

## F3 · 释放时报「无法识别其中的生物」

**发现时间**：2026-10-03 第三轮人工验收
**现象**：四个实体与原版狼**都能收纳**，但释放时统一提示
「无法识别其中的生物（可能来自已移除的模组）」。

### 定位过程

释放路径的第一行诊断就把 NBT 形状打了出来，一次命中：

```
物品根键=[EntityType, EntityData, StoredAt]        ← EntityType 写到了【物品根】
EntityData 键=[Brain, ..., Owner, ..., UUID, ...]  ← EntityData 里【没有】EntityType
记录的实体 id=（空）  反查类型=null
```

### 根因：写入位置与读取位置不一致（违反自己定义的契约）

| | 代码 | 位置 |
| :--- | :--- | :--- |
| **写入** | `itemTag.putString(StorageToolNbt.ENTITY_TYPE, ...)` | 物品**根** |
| **读取** | `data.getString(StorageToolNbt.ENTITY_TYPE)` | `EntityData` **内部** |

而 `StorageToolNbt` 的类注释与 `ENTITY_TYPE` 的 javadoc **都写明它属于 `EntityData` 内部**。
即：**实现违反了自己在 T1 定义的数据契约。**

数据本身是完整的（`EntityData` 内 35 个实体键俱在），只是类型 id 存错了位置、读错了位置。

### 修法

```java
// 类型 id 与实体数据写在一起，与契约一致
data.putString(StorageToolNbt.ENTITY_TYPE, entityTypeId(entity));
itemTag.putLong(StorageToolNbt.STORED_AT, entity.level().getGameTime());
itemTag.put(StorageToolNbt.ROOT, data);
```

`clearEntityData` 相应收敛（`ENTITY_TYPE` 随 `ROOT` 一起被移除，不再当根键删）。

### 教训

1. **契约写在注释里等于没有契约** —— 编译器不会检查「键该放在哪一层」。
   → 优化项 **O-24**：给 `StorageToolNbt` 加 `write`/`read` 方法对，
   让键名不出现在业务代码里，从「可能写错」变成「不可能写错」。
2. **诊断信息要打「结构」而不是「结论」**：这次能一次命中，是因为日志打了
   `物品根键=[...]` 与 `EntityData 键=[...]`，直接暴露了键的层级。
   如果只打「读到的类型为空」，还要再猜一轮。

## F1/F2/F3 共同暴露的流程缺陷

三次都是**用户先发现、我才知道**。根因不是能力问题，而是**我的验证策略有洞**：

| 洞 | 后果 | 处置 |
| :--- | :--- | :--- |
| **判定/转换逻辑是纯函数却没有测试** | F1（空符拒收）一个断言就能拦 | 优化项 **O-17**：引入 JUnit 补断言 |
| **「物品与数据的绑定」没有契约约束** | F1、F2、F3 全都出在这里 | 优化项 **O-21**（统一数据流向）、**O-24**（NBT 读写强制走契约方法） |
| **T1~T6 只做了「编译通过」验证** | 编译通过 ≠ 功能正确，这是**结构性**缺口 | 优化项 **O-22**：无头 game test 从「可选」提升为 P0 |
| **验收指令写得不严谨** | 我曾让用户「重启后右击地面复验」，但用户手上只有修复前的空符 —— 该步骤从设计上就不可能通过 | 交付验证步骤时必须写明**前置状态**（「先重新收纳一次再释放」） |

> **诚实结论**：T1~T5 我报告的「验证通过」实际只覆盖了**编译与 datagen**，
> 完全没覆盖运行时行为。三轮返工是验证策略不足导致的，不是运气问题。
> 这也是把「加运行时验证」排进优化项的根本原因。

### 一个正面收获

诊断日志虽然最终被精简掉（正常路径零输出），但**它的设计方式值得保留**：

1. **在判定链的每一环打点**，而不是只打最终结论 —— F1 与 F3 都是一次命中；
2. **打「结构」而非「结论」** —— 打出 NBT 的键列表，比打出「类型为空」有用得多；
3. **出错路径的断言要留在代码里**（如 `swapToFullTool` 里的「换符后必须有数据」自检），
   正常路径的日志则全部移除。
